Section 01

Introduction

sluice is an open-source Go library that sits between high-velocity event streams — SQS queues, Kafka topics, webhook floods — and a document store such as AWS DocumentDB or MongoDB. It plays two roles at once, and the tension between those roles is what makes the design interesting.

On the write side it is a velocity shield: every incoming event is absorbed into a Redis-backed state journal in sub-millisecond time and acknowledged immediately, while background flushers quietly coalesce thousands of events into a handful of bulk upserts. The document store never sees the storm; it sees a calm, ordered trickle.

On the read side it is a hot-state journal: the same Redis structure that absorbed the writes becomes the authoritative, sub-millisecond read surface for the small subset of keys that are actually active right now — a logged-in user, an open session, an HTTP handler reading back what it just wrote. Cold keys fall through to the document store transparently.

The one-sentence thesis. Treat Redis not as a cache in front of your database, but as a durable, deduplicating write journal that also happens to be the fastest possible read path for whatever is currently hot.

The library was born in ad-tech, where millions of customers receive nudges, bids and inventory updates at rates no single document-store primary can absorb. But the shape of the problem — wide, incoherent, spiky write traffic against a store optimised for coherent bulk work — appears everywhere: loyalty platforms, payment ledgers, IoT telemetry, session-state services. sluice generalises the pattern behind a small, contract-driven API.

Section 02

The core problem it solves

Modern event-driven platforms do not produce database-friendly traffic. They produce wide-breadth, incoherent, spiky traffic: one event, one customer, one field changed, arriving unbatched and uncoordinated from dozens of consumer workers. A nudge-inventory stream at 100K TPS is not 100K updates to a few documents — it is 100K updates spread across 80–90K different documents, with a long tail of keys that receive three or four events within the same second.

Forwarding that traffic naively to a document store produces four compounding failures.

① Single-primary bottleneck

DocumentDB and MongoDB route all writes through one primary. Every individual event is a separate network round-trip against a node that cannot scale horizontally for write throughput.

② Index multiplication

Each secondary index multiplies the I/O cost of every single write. Four indexes on a hot collection means four B-tree mutations per event, per write.

③ Connection-pool saturation

DocumentDB hard-caps connections per instance class. A spike that wakes 200 consumer workers exhausts the pool, and latency collapses for everyone, including unrelated readers.

④ Round-trip explosion

100,000 events touching 80,000 unique customers become 100,000 individual round-trips — when the same work is ~100 BulkWrite calls of ~1,000 upserts each.

Figure 1 · The naive path — every event is a round-trip

Six events, six round-trips, three of them redundant. At 100K TPS this is 100K round-trips against one node.

Why the obvious fixes fail

“Just batch inside the consumer.” Consumers are stateless and horizontally scaled. Two workers holding events for the same key cannot see each other, so cross-consumer coalescing is impossible without a shared store — which is exactly the thing we are trying to protect. Worse, in-memory batching loses everything in the buffer the moment a pod dies.

“Put a cache in front.” A cache has the wrong semantics. Caches are read-optimised; their TTL is a staleness budget; a miss means “go ask the database”; and eviction under pressure silently destroys data. None of that is what a write-absorbing layer needs.

The insight. Decouple the ingest rate from the persistence rate using a store that is fast enough to acknowledge every event individually (Redis) and structured enough to replay its contents in bulk later (a journal, not a cache).

Section 03

Architecture

The architecture has three load-bearing ideas: an atomic journal write, band partitioning that makes the whole thing cluster-safe and parallel, and a multi-trigger flush engine bound together by a two-phase commit. Everything else — dedup, idempotency, dead-letters, the hot regime — hangs off those three.

3.1 · The atomic journal write

Every Write() executes a single pre-loaded Lua script that performs three Redis operations in one network round-trip: store the payload, arm its crash-recovery TTL, and mark the key dirty. Because it is one script, there is no window in which the payload exists but the key is unmarked, or vice-versa.

Figure 3 · One script, three operations, one round-trip

consumer worker

① HSET sl:ns:payload:{band}:user → p=payload, ts=now, h=hash

③ ZADD sl:ns:dirty:{band} → score=now, member=user
ACK nil
< 1 ms

The ZADD score is the event timestamp in milliseconds — the flush engine therefore always drains oldest-first, giving a natural staleness bound equal to FlushWindow.

The payload hash carries three fields: p (opaque bytes — sluice never interprets them), ts (the score), and optionally h (an xxHash64 content fingerprint when deduplication is enabled). The KeyTTL on the hash is the safety net: if the process dies before a flush, the key self-cleans instead of pinning memory forever, and the pre-eviction trigger (§3.4) makes sure legitimate payloads are flushed long before that TTL bites.

3.2 · Coalescing: why wide traffic collapses

ZADD on an existing member only updates its score; it does not create a second entry. And HSET overwrites the payload in place. Together these two properties mean that N events for the same correlation key within one flush window collapse into one dirty-set entry holding the latest payload. The document store only ever sees final state per window — intermediate churn never reaches it.

Coalescing is free: it falls out of ZSET/HSET semantics. No locks, no coordination, no consumer-side state.

3.3 · Bands, hash tags, and cluster safety

The dirty queue is not one sorted set — it is sixteen (configurable) of them, called bands. A correlation key's band is FNV-32a(key) % bandCount, and each band is drained by its own goroutine. This gives parallelism without coordination: bands never share state.

Bands also solve the Redis Cluster problem. Every key sluice writes embeds the band as a {band} hash tag, so the payload hash, the dirty set, the hot marker, the index keys and the idempotency guard for a given key all land on the same cluster slot. That is what makes the atomic Lua script, the HMGET pipelines and the SINTER queries legal under cluster mode — and on Valkey clusters, which enforce the same rule.

3.4 · The flush engine: four triggers

One goroutine per band sleeps until any of four independent triggers fires. The set of triggers is the engine's entire policy: each one defends against a different failure mode, and together they bound latency, memory, and data loss simultaneously.

The pre-eviction poller runs every KeyTTL/2 (min 1s) and is disabled when KeyTTL ≤ 0.

3.5 · Two-phase commit and crash safety

The dirty set is the source of truth for “what still needs persisting”. Keys are removed from it only after the document store confirms the write. If the process crashes between the BulkWrite and the ZREM, the next cycle re-flushes those keys — and because every sink operation is an upsert with last-write-wins semantics, the replay is harmless. That single ordering rule is what upgrades the pipeline from at-most-once to at-least-once with idempotent effect.

Figure 7 · Commit ordering, and the crash window

Permanent failures (code 11000, contract violations) take a different exit: the dead-letter set (§3.6).

3.6 · Write-path resilience: dedup, idempotency, dead-letters

Content deduplication. High-velocity streams re-send unchanged payloads constantly — heartbeats, periodic full-state refreshes, at-least-once redeliveries. With WithContentDedup(true), each payload is fingerprinted with xxHash64 and compared against the stored h field inside the same Lua script. On a match, sluice refreshes the payload TTL and returns — skipping the dirty-set insertion, index maintenance and volume signalling entirely. The document store never sees a write it already has.

Figure 8 · Dedup decision inside the atomic script

Write(user, payload)
h = xxhash64(payload)
h == stored h ?
yes
EXPIRE only · return 0 · store untouched
no
HSET p,ts,h · EXPIRE · ZADD · return 1

Disabled by default: it costs one extra hash field per key.

Idempotent writes. Upstream queues redeliver. WriteIdempotent(ctx, user, payload, msgID) guards the entrance with a SETNX EX on sl:ns:idem:{band}:key; a replay returns ErrDuplicateIdempotencyKey so the consumer can ACK and move on without polluting the journal. The guard's TTL (IdempotencyTTL, default 4h) should match your upstream's redelivery window, not your retention needs.

Dead-letter queue. When a flush meets a permanent failure — a unique-index violation (code 11000) or a contract violation — retrying is futile and would wedge the band. Those keys move to a per-band dead-letter ZSET, their payload TTL extended to seven days for inspection, annotated with the failure reason. Transient failures stay in the dirty set and retry automatically. Three recovery strategies drain the DLQ:

Figure 9 · DLQ recovery strategies

DLQIgnore

Log each record, remove it. For expected, safely-discardable failures.

DLQUpsert

Re-run the WriteContract with Upsert:true. Pairs with the payload-healing pattern: flip an atomic flag, and the contract corrects bad fields at recovery time.

DLQReInsert

Mutate the correlation key (timestamp suffix) and re-enqueue. Keeps original and corrected documents side-by-side.

ProcessDLQ is context-aware; WithDLQAutoProcess(interval, strategy) runs it on a background ticker.

Degraded mode. If Redis itself is unavailable, sluice refuses to drop data: with DegradedModeDirect(true) (the default) each Write() applies the contract and calls sink.Write directly — slow, but correct. With it disabled, writes return ErrRedisUnavailable so the caller can decide.

Section 04 · The centrepiece

The Hot & Cold regime

Here is the observation that turns sluice from a write buffer into a data platform: a wide-breadth stream is not uniformly wide. At any instant, a small subset of correlation keys is alive — a user is logged in, a session is open, an HTTP handler is about to read back the key it just wrote. The other ninety percent are background churn that only the document store cares about. Treating those two populations identically wastes the journal's best property: it is already holding the freshest possible copy of exactly the keys people are asking about.

sluice therefore runs two regimes over one journal. Cold keys are pure transit: absorbed, coalesced, flushed, evicted. Hot keys are promoted to resident state: warmed from the document store on login, served in sub-millisecond time for the length of the session, and kept fresh by the very traffic that touches them.

4.2 · Promotion: the HotLoad lifecycle

Promotion is explicit and cheap. HotLoad(ctx, user) asks the ReadContract for a datastore-agnostic ReadModel, executes it through the configured Source, seeds the journal with the returned bytes, and sets the hot marker with an ActivityWindow TTL. From that moment the session's reads never touch the document store again.

Figure 12 · One session, three phases

HotLoad and the cold fallback both require WithSource() + WithReadContract(); Build() fails fast if one is missing.

4.3 · Serving reads: lazy refresh, no goroutine storms

A hot read is one pipelined round-trip: HGET for the payload and PTTL for the remaining life, fetched together. The PTTL is not telemetry — it drives the refresh policy. If the remaining TTL has fallen below 20% of ActivityWindow, sluice refreshes the hot marker and payload TTL synchronously, inline. Steady read traffic therefore keeps a key hot indefinitely; silence lets it age out and demote itself.

Why synchronous and not fire-and-forget? An earlier design spawned a background goroutine per read to refresh the TTL. At 100K reads/sec that is 100K goroutines/sec, each holding a context and a pooled connection — a self-inflicted goroutine storm on the hot path. The lazy threshold check costs one comparison and fires a refresh only in the last fifth of the window.

Hot-aware flush adds a second refresher: after each successful commit, committed keys' TTLs are extended to ActivityWindow.

The second refresher matters more than it looks. Without it, a flush would be self-defeating for hot keys: the payload's 30-second transit TTL would expire right after being written, evicting the very session the flush was meant to serve. WithHotAwareFlush(true) (the default) extends every committed key's TTL to ActivityWindow after a successful commit, so a flush can never evict a live session. Writes to hot keys additionally raise the hot trigger, pulling that band's flush forward from 250 ms to under 10 ms — which is what makes “write then immediately read your own write” behave correctly for sync APIs.

4.4 · The journal as a queryable store

Because hot keys and in-flight writes are already resident, the journal can answer questions about live state without touching the document store at all. An optional IndexContract projects fields out of each payload as it lands; sluice maintains them through a Go-side pipeline — no Lua, no cjson, so the path is safe on Valkey as well as Redis.

At least one equality filter is required. Query sees resident state only — a live-state lookup, not a replacement for store queries.

4.5 · Memory economics: two honest profiles

Hot-aware flush has a memory consequence you should choose deliberately: it extends the TTL of every successfully committed key, not only the marked-hot ones. That gives you two distinct residency profiles, and the right one depends on whether your service has a read path.

ProfileSettingRedis residencyUse when
Transit bufferWithHotAwareFlush(false)~25K keys at peak; governed by in-flight writes; 30 s lifepure write-through ingest, no read path
Session storeWithHotAwareFlush(true) (default)governed by concurrent active sessions; 4 h lifeany service serving sync reads for active users

Demotion needs no machinery: a hot key that goes quiet simply stops being refreshed, its marker and payload expire, and the next Read() transparently falls back to the Source. The regime is self-balancing — memory tracks activity, not history.

Section 05

The library APIs

The public surface is deliberately small: a builder, three contracts, and eight verbs. Everything else lives behind interfaces you implement (FlushSink, Source, MetricsRecorder).

5.1 · Construction and lifecycle

// Build a fully-wired instance. Contracts are the only domain code you write.
s, err := sluice.New("nudge_inventory").
    WithRedis(sluice.RedisConfig{Addrs: []string{"redis:6379"}}).
    WithSink(sk).                      // write side  (required)
    WithWriteContract(contract).       // write side  (required)
    WithSource(src).                   // read side   (with ReadContract)
    WithReadContract(readContract).    // read side
    WithIndexContract(indexContract).  // enables Query()
    Build(ctx)
defer s.DrainAndClose(ctx)          // flush in-flight, stop batcher & DLQ ticker

5.5 · The three contracts

WriteContract

(user, payload) → *WriteModel

Translates opaque bytes into a resolved upsert (Filter / Update / Upsert). Called once per key per flush — never on the Write() hot path.

ReadContract

(user) → *source.ReadModel

Returns a datastore-agnostic filter. The Source executes it — your domain code never imports a driver.

IndexContract

(user, payload) → map[string]any

Projects index fields: strings become equality SETs, numbers become range ZSETs, anything else is ignored.

5.6 · Pluggable persistence, both directions

// write side
type FlushSink interface {
    BulkWrite(ctx, models) (*BulkWriteResult, error)
    Write(ctx, model) error      // degraded mode
    Ping(ctx) error
    Close(ctx) error
}
// read side — symmetric by design
type Source interface {
    Read(ctx, model) ([]byte, error)
    Ping(ctx) error
    Close(ctx) error
}

sink/docdb and source/docdb ship in the box; NewSourceWithClient(sk.Client(), …) runs both paths over a single Mongo connection pool. source.ErrRecordNotFound is translated to the public sluice.ErrRecordNotFound, so callers never import the source package for error handling.

5.7 · Telemetry and errors

MetricsRecorder exposes eleven hooks; the three regime-specific ones are the ones to alert on. RecordRead(ns, d, isHot, err)'s isHot flag is your hot-hit ratio: a falling ratio means sessions are ageing out before their traffic finishes, i.e. ActivityWindow is too short. RecordWarmUp tracks HotLoad latency; RecordHotSetSize tracks resident hot keys — your Redis memory forecast.

6.4 · Three reference profiles

// ① Pure ingest — no read path. Transit-buffer memory profile.
sluice.New(ns).WithRedis(rc).WithSink(sk).WithWriteContract(wc).
    WithHotAwareFlush(false).            // 30s residency, ~25K keys at peak
    WithBatchedWrites(200, 5*time.Millisecond).
    WithContentDedup(true).
    Build(ctx)
// ② Mixed workload — the defaults are already this profile.
sluice.New(ns).WithRedis(rc).WithSink(sk).WithWriteContract(wc).
    WithSource(src).WithReadContract(rc2).WithIndexContract(ic).
    Build(ctx)                            // 4h window, hot-aware flush on
// ③ Read-heavy session service — long sessions, aggressive dedup.
sluice.New(ns).WithRedis(rc).WithSink(sk).WithWriteContract(wc).
    WithSource(src).WithReadContract(rc2).
    WithActivityWindow(8 * time.Hour).
    WithContentDedup(true).
    WithFlushWindow(500 * time.Millisecond).  // reads served from journal; relax store lag
    Build(ctx)
Tuning heuristics that have held up in production.
  • Set FlushWindow to the staleness your readers tolerate — nothing else bounds it.
  • Set KeyTTL ≥ 4× FlushWindow so a stalled flusher never loses payloads to TTL.
  • Set ActivityWindow from session length (p95 login-to-logout), not from memory fear; watch RecordHotSetSize instead.
  • Enable WithBatchedWrites only when per-write Redis latency, not DocumentDB, is the bottleneck.

Section 07

Closing

sluice is best understood as three decisions stacked on each other. First, that Redis should be used as a journal rather than a cache, which buys atomic absorption and free coalescing. Second, that band partitioning with hash tags makes the journal parallel and cluster-legal by construction rather than by care. Third, that the journal's contents are worth serving back — which is what the hot/cold regime exploits, turning a write-optimised buffer into the fastest read path in the system for exactly the keys that matter right now.

The result is a library where the caller contributes three small functions and receives, in exchange, a crash-safe, deduplicating, idempotent, cluster-aware, self-healing data plane with a dead-letter queue and a sub-millisecond read path — validated end-to-end against real Redis, Valkey-cluster, MongoDB, Kafka and SQS in CI.
