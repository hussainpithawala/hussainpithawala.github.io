Section 01

Introduction

sluice is an open-source Go library that sits between high-velocity traffic (SQS queues, Kafka topics, webhook floods, synchronous HTTP and gRPC APIs) and a system of record. It ships first-class adapters for AWS DocumentDB / MongoDB, AWS DynamoDB and PostgreSQL, and two small interfaces let you bring your own store. It plays two roles at once, and the tension between them is what makes the design interesting.

On the write side it is a velocity shield. Every incoming event is absorbed into a Redis-backed state journal in sub-millisecond time and acknowledged, while background flushers coalesce thousands of events into a handful of bulk writes. The datastore never sees the storm; it sees a calm, ordered trickle.

On the read side it is a hot-state journal. The same Redis structure that absorbed the writes becomes the authoritative read surface for the keys that are active right now: a logged-in user, an open session, an HTTP handler reading back what it just wrote. An optional in-process L1 sits in front of it for sub-microsecond reads, and cold keys fall through to the datastore transparently.

The one-sentence thesis. Treat Redis not as a cache in front of your database, but as a durable, deduplicating write journal that also happens to be the fastest possible read path for whatever is currently hot, and that never expires anything it has not yet persisted.

The library was born in ad-tech, where millions of customers receive nudges, bids and inventory updates at rates no single primary can absorb. But the shape of the problem (wide, incoherent, spiky write traffic against a store optimised for coherent bulk work) appears everywhere: loyalty platforms, payment ledgers, IoT telemetry, session-state services. sluice generalises the pattern behind a small, contract-driven API.

Section 02

The core problem it solves

Event-driven platforms do not have a data-volume problem; they have a data-velocity problem. They produce wide-breadth, incoherent, spiky traffic: one event, one customer, one field changed, arriving unbatched and uncoordinated from dozens of consumer workers. A nudge-inventory stream at 100K TPS is not 100K updates to a few records. It is 100K updates spread across 80–90K different records, with a long tail of keys that receive three or four events within the same second.

Forwarding that traffic naively to a datastore produces four compounding failures.

① Single-primary bottleneck

DocumentDB, MongoDB and PostgreSQL route all writes through one primary. Every individual event is a separate round-trip against a node that cannot scale horizontally for write throughput.

② Per-write cost multiplication

Each secondary index multiplies the I/O of every write. On DynamoDB the same burst becomes WCU spend, and every GSI you add for lookups multiplies it again.

③ Connection-pool saturation

DocumentDB caps connections per instance class, and PostgreSQL pays a backend process and a transaction per write. A spike that wakes 200 workers exhausts the pool, and latency collapses for everyone, including unrelated readers.

④ Round-trip explosion

100,000 events touching 80,000 unique customers become 100,000 round-trips, when the same work is ~100 bulk writes of ~1,000 records each. Reads suffer the same way: assembling a user's working set is N+1 lookups.

Figure 1 · The naive path: every event is a round-trip

Six events, six round-trips, three of them redundant. At 100K TPS this is 100K round-trips against one node.

Why the obvious fixes fail

“Just batch inside the consumer.” Consumers are stateless and horizontally scaled. Two workers holding events for the same key cannot see each other, so cross-consumer coalescing is impossible without a shared store, which is exactly the thing we are trying to protect. Worse, in-memory batching loses everything in the buffer the moment a pod dies.

“Put a cache in front.” A cache has the wrong semantics. Caches are read-optimised; their TTL is a staleness budget; a miss means “go ask the database”; and eviction under pressure silently destroys data. None of that is what a write-absorbing layer needs.

Traditional cache sluice Redis journal
Optimised for Reads; avoids re-computation Writes; absorbs velocity, then serves reads off the absorbed state
TTL means Staleness budget for reads Residency after the store confirms a write. Unflushed state has no TTL at all
On miss Go to the database Read the Source, then hydrate the journal, but only if it is still a miss
Under pressure Eviction silently loses data Runs with noeviction: a full Redis refuses writes loudly instead of dropping state
The insight. Decouple the ingest rate from the persistence rate using a store that is fast enough to acknowledge every event individually (Redis) and structured enough to replay its contents in bulk later (a journal, not a cache).

Section 03

The write path

The write path has three load-bearing ideas: an atomic journal write, band partitioning that makes the whole thing cluster-safe and parallel, and a multi-trigger flush engine whose commits are conditional on a per-key sequence. Everything else (dedup, idempotency, dead-letters, the hot regime) hangs off those three.

3.1 · The atomic journal write

Every Write() executes a single pre-loaded Lua script that performs four Redis operations in one network round-trip: store the payload, bump its sequence, strip any TTL, and mark the key dirty. Because it is one script, there is no window in which the payload exists but the key is unmarked, or vice versa.

Figure 3 · One script, four operations, one round-trip

caller
Write(user, payload)

EVALSHA write · single round-trip

① HSET sl:ns:payload:{band}:user → p=payload, ts=now
② HINCRBY payload v 1 → per-key sequence
③ PERSIST payload → unflushed state never expires
④ ZADD sl:ns:dirty:{band} → score=now, member=user
return nil
< 1 ms · safe to ack

The ZADD score is the event timestamp in milliseconds, so the flush engine always drains oldest-first, giving a natural staleness bound equal to FlushWindow.

The payload hash carries four fields: p (opaque bytes; sluice never interprets them), ts (the score), v (the sequence, used by the conditional commit in §3.5) and, optionally, h (an xxHash64 content fingerprint when deduplication is on).

Why PERSIST, and what changed in 1.0.8. Up to 1.0.7, every write armed a KeyTTL (30 s) on the payload as a “crash-recovery net”, and the drain quietly skipped dirty keys whose payload had expired. A sink outage longer than 30 s therefore dropped acknowledged writes with no metric and no log. Now unflushed payloads are persistent, and a TTL is applied only after the sink confirms the write. Omitting EXPIRE alone would not be enough: HSET keeps whatever TTL a previously flushed version of the key had, so the script has to PERSIST explicitly.

Write returning nil means exactly one thing: the entry is in Redis and safe to acknowledge upstream. That holds in batched mode too (§3.6). On an error, don't ack.

3.2 · Coalescing: why wide traffic collapses

ZADD on an existing member only updates its score; it does not create a second entry. And HSET overwrites the payload in place. Together these two properties mean that N events for the same correlation key within one flush window collapse into one dirty-set entry holding the latest payload. The datastore only ever sees final state per window; intermediate churn never reaches it.

Coalescing is free: it falls out of ZSET/HSET semantics. No locks, no coordination, no consumer-side state.

3.3 · Bands, hash tags, and cluster safety

The dirty queue is not one sorted set but sixteen (configurable), called bands. A correlation key's band is FNV-32a(key) % bandCount, and each band is drained by its own goroutine. This gives parallelism without coordination: bands never share state.

Bands also solve the Redis Cluster problem. Every per-key and per-band key embeds the band as a {band} hash tag, so the payload hash, dirty set, hot marker, index keys and idempotency guard for a given key all land on the same cluster slot. That is what makes the Lua scripts, the HMGET pipelines and the SINTER queries legal under cluster mode, and on Valkey clusters, which enforce the same rule.

3.4 · The flush engine: four triggers

One goroutine per band sleeps until any of four independent triggers fires. The set of triggers is the engine's entire policy: each defends against a different failure mode, and together they bound latency, memory and backlog at once. The engine starts only when both a sink and a WriteContract are configured.

3.5 · Conditional commit and crash safety

The dirty set is the source of truth for “what still needs persisting”. Keys are removed from it only after the datastore confirms the write. If the process crashes between the bulk write and the commit, the next cycle re-flushes those keys, and because every sink operation is an upsert, the replay is harmless. That ordering rule is what makes the pipeline at-least-once with idempotent effect.

1.0.8 adds a second rule. Up to 1.0.7 the commit removed flushed keys from the dirty set by name, so a newer write to the same key that landed while the batch's bulk write was in flight lost its dirty entry and never reached the store. Now the drain reports each key's sequence (FlushRecord.Seq), and the engine commits through CommitFlushed: one atomic script per key that removes the dirty entry and applies the post-flush TTL only if v is unchanged. Dead-lettering is conditional the same way (DeadLetterIfUnchanged), so a failure on a superseded payload never dead-letters its replacement.

The engine never infers success. Each bulk write result is handled per key:

3.6 · Write-path resilience: dedup, idempotency, batching, dead-letters, degraded mode

Content deduplication. High-velocity streams re-send unchanged payloads constantly: heartbeats, periodic full-state refreshes, at-least-once redeliveries. With WithContentDedup(true), each payload is fingerprinted with xxHash64 and compared against the stored h field inside the same Lua script. On a match the write skips the dirty set, index maintenance and the flush entirely; the datastore never sees a write it already has.

Figure 8 · Dedup decision inside the atomic script

Write(user, payload)
h = xxhash64(payload)
h == stored h ?
yes
no dirty entry · if already flushed, extend TTL only · return 0
no
HSET p,ts,h · HINCRBY v · PERSIST · ZADD · return 1

A duplicate never adds a TTL to an unflushed payload, and only ever extends a flushed one, so a hot key's longer TTL is never shortened. Off by default: it costs one extra hash field per key.

Idempotent writes. Upstream queues redeliver. WriteIdempotent(ctx, user, payload, msgID) guards the entrance with a SETNX EX on sl:ns:idem:{band}:msgID; a replay returns ErrDuplicateIdempotencyKey so the consumer can ack and move on without polluting the journal. The guard's TTL (IdempotencyTTL, default 4h) should match your upstream's redelivery window, not your retention needs.

Batched writes that ack honestly. WithBatchedWrites(size, window) lets concurrent writers share one Redis pipeline: ⌈N / size⌉ round-trips instead of N. Up to 1.0.7, Write() returned nil as soon as the entry was buffered, and a failed pipeline was only logged, after every caller in it had already acked upstream. Now each Write waits for its own entry and returns that entry's real error, so a failed batched write falls back to degraded mode or reaches the caller. The batcher also runs until DrainAndClose rather than until the Build context is cancelled.

Dead-letter queue. When a flush meets a permanent failure, retrying is futile and would wedge the band. Those keys move to a per-band dead-letter ZSET with their payload kept for seven days and the failure reason recorded. Each bundled sink isolates a permanent failure to the offending rows (§7.2), so one poison record never stalls its band; the rest of the batch commits.

Figure 9 · DLQ recovery strategies

DLQIgnore

Log each record, remove it. For expected, safely discardable failures.

DLQUpsert

Re-run the WriteContract and force an upsert. Pairs with the payload-healing pattern: set a flag, and the contract repairs bad fields at recovery time.

DLQReInsert

Re-enqueue under a mutated key (WithKeyMutator; a timestamp suffix by default), keeping both documents.

ProcessDLQ is one-shot across all bands; WithDLQAutoProcess(interval, strategy) runs it on a background ticker. A sink error with no correlation key aborts the commit in DLQ replay too.

Order-safe degraded mode. If a Redis write fails, WithDegradedModeDirect(true) (the default) can write straight to the datastore. Up to 1.0.7 it always did, even when an older version of the same key was still pending in Redis; that older version's later flush then overwrote the newer data. Now degraded mode first checks whether anything is pending for the key (the dirty set and the DLQ, both readable even under noeviction OOM) and writes directly only when nothing is. Otherwise, including when Redis is unreachable and pending versions cannot be ruled out, Write returns ErrDegradedWriteUnsafe without persisting anything. The caller retries, and the write goes through Redis in order.

Behaviour change. During a full Redis outage, degraded-mode writes now return errors instead of going direct. Callers must not ack those upstream; they are counted as op="degraded_refused".

Script-cache recovery. After a Redis restart, failover or SCRIPT FLUSH, a pre-loaded script SHA is gone. Every Lua call site now reloads and retries once on NOSCRIPT, where some paths previously failed until the process restarted.

Section 04 · The centrepiece

The read path: hot & cold

Here is the observation that turns sluice from a write buffer into a data platform: a wide-breadth stream is not uniformly wide. At any instant, a small subset of correlation keys is alive: a user is logged in, a session is open, an HTTP handler is about to read back the key it just wrote. The rest is background churn that only the datastore cares about. Treating those two populations identically wastes the journal's best property: it already holds the freshest possible copy of exactly the keys people are asking about.

sluice therefore runs two regimes over one journal. Cold keys are pure transit: absorbed, coalesced, flushed, then expired shortly after. Hot keys are promoted to resident state: warmed from the datastore on login, served in sub-millisecond (or, with L1, sub-microsecond) time for the length of the session, and kept fresh by the very traffic that touches them.

4.2 · Tiered reads: each tier heals the one above it

A read falls through three tiers. L1 is an optional in-process LRU. L2 is the Redis journal: the authoritative live state and the write buffer. L3 is your datastore, reached through a Source and a ReadContract. A hit at any tier fills the tiers above it.

Hydration never lies. Read-through, HotLoad and ReadBulk hydration go through a Lua primitive that seeds the journal only on a miss. Every write reaches the journal before the store, so an existing entry (pending, flushed or dead-lettered) is always at least as new as a store read; it wins and only its TTL is extended. Hydrated data is never added to the dirty set, so store data is never flushed back to the store and reader-only pods never build a backlog. Up to 1.0.7, hydration used the regular write path and did both of those things.

Lazy TTL refresh. The PTTL fetched with every L2 hit is not telemetry; it drives the refresh policy. When the remaining TTL falls below 20% of ActivityWindow, the read schedules a short, bounded refresh of the payload and marker off the read path. Steady read traffic therefore keeps a key hot indefinitely; silence lets it age out and demote itself. Refreshes are extend-only and skip unflushed payloads, so a read can never put a TTL on data that has not reached the store.

4.3 · Promotion: fire-and-forget HotLoad

Promotion is explicit and cheap. In 1.0.8, HotLoad(ctx, user) returns only an error: it sets the hot marker synchronously and returns, then hydrates the payload, the L1 cache and the indexes in the background. A login handler is never blocked on a cold store read. If a caller needs the payload immediately, it calls Read afterwards, which is served from whichever tier has it.

Figure 14 · One session, three phases

Dependencies are checked at call time: HotLoad returns ErrMissingSource or ErrMissingReadContract if the read path is not configured. A kind=seed broadcast goes out only when the payload was actually hydrated.

Writes to hot keys raise the hot trigger, pulling that band's flush forward from 250 ms to under 10 ms, which is what makes “write, then immediately read your own write” from another service behave correctly. With WithHotAwareFlush(true) (the default), a committed key that still has a live hot marker gets ActivityWindow instead of KeyTTL, so a flush can never evict a live session.

4.4 · The L1 local journal and cross-pod convergence

An optional, sharded in-process LRU (256 shards) sits in front of the journal. Writes go through to the local L1, so a same-pod Read() after Write() returns in sub-microseconds. They are also broadcast to peer pods on a Redis Stream, sl:{ns}:bcast. The XADD piggy-backs on the journal write's pipeline, so the broadcast costs no extra round-trip, and peer pods converge within milliseconds.

4.5 · The journal as a queryable store

Because hot keys, bulk-loaded sets and in-flight writes are already resident, the journal can answer questions about live state without touching the datastore. An optional IndexContract projects fields out of each payload as it lands (and an IndexBulkContract does the same for ReadBulk results). sluice maintains the indexes through a Go-side pipeline, with no Lua and no cjson, so the path is safe on Valkey as well as Redis.

Figure 16 · Index types and the Query() pipeline

At least one equality filter is required. Index maintenance is best-effort and never fails the primary write.

Indexes follow their payloads. Up to 1.0.7, index entries of cold keys lingered for up to ActivityWindow after their 30 s post-flush payload had expired, until a full sweep (a ~4 minute pass) reached them, so Redis memory grew without bound under sustained write load. Now, whenever a payload gets or extends a TTL, it is also scored into a per-band index expiry queue (sl:ns:idxexp:{band}). A pruner drains it every second and removes index entries within about a second of their payload expiring. Its cost is proportional to what expires, not to index size, and it re-checks liveness, so a live or re-written key is never pruned. The full sweep (WithIndexSweepInterval, default 15 s per band) remains as a safety net.

4.6 · Memory economics

Redis memory tracks two things: your active-key count and your in-flight backlog, not your total key space. Each class of key has exactly one rule:

Key state Residency Governed by
unflushed (any key)no TTL until committedwrite rate × store availability; size Redis for the worst-case backlog
flushed, coldKeyTTL (30 s)recent write breadth
flushed, hotActivityWindow (4 h), re-armed per flush, extended by readsconcurrent active sessions
hydrated / bulk-loadedActivityWindowworking sets you chose to load
index entriespruned within ~1 s of their payloadthe payloads above
Fixed in 1.0.8. Up to 1.0.7, hot-aware flush extended every flushed key's TTL to ActivityWindow, not only hot ones, inflating Redis memory by orders of magnitude for write-heavy services. Now cold keys get KeyTTL after flush and only keys with a live hot marker get ActivityWindow. The TTL and hot-marker refresh run as three pipelines per flush batch rather than per-key round-trips.

Demotion needs no machinery: a hot key that goes quiet stops being refreshed, its marker and payload expire, its index entries are pruned, and the next Read() falls back to the Source. The regime is self-balancing; memory tracks activity, not history.

Section 05 · New in 1.0.8

Many access patterns are set-shaped: “all active campaigns for this user”, “the last 50 transactions on this account”. Assembling them key by key is the N+1 problem on the read side. ReadBulk runs one set-based query for a lookup key, then hydrates every returned item into L2, the secondary indexes and L1. After that, per-key Read and Query never touch the store.

Read-your-writes. Bulk hydration uses the same miss-only primitive as read-through. For a key already in the journal (for example, a pending Write), ReadBulk returns and mirrors into L1 the journal payload, not the store's, so stale store data never masks a newer write. Bulk-hydrated items live for ActivityWindow. sluice does not cap projector output, so bound your queries with LIMIT, SetLimit or QueryInput.Limit. A natural deployment is a bulk pre-warmer job that loads active users' working sets ahead of peak traffic (§7.3).

Section 06 · Hardened in 1.0.8

The durability model

A velocity platform is only useful if acknowledged data is never silently lost. The 1.0.8 release audited every path between Write returning nil and the datastore confirming the record, and adopted one rule throughout: prefer a loud failure to a quiet drop.

Figure 18 · The life of a payload's TTL

Writenil = journaled · ack
unflushedPERSIST · no TTL · dirty
store confirmsper key, attributed
commit if v unchangedTTL = KeyTTL or ActivityWindow
expiryindexes pruned ~1 s later

The only way out of the unflushed state is a confirmed, attributed commit, or the DLQ.

Guarantee How
Ack means journaledWrite returns nil only after its entry is in Redis, in batched mode too: each caller gets its own entry's result.
Unflushed never expiresPayloads are persistent until the sink confirms them. TTLs apply only after a commit, and every TTL refresh is extend-only.
Commits can't lose writesEvery write bumps a per-key sequence; commit and dead-lettering are conditional on it. A write that races an in-flight flush stays dirty.
No commit without attributionA sink error with no correlation key aborts the commit for the whole batch, in the flush engine and in DLQ replay. Nothing is committed just because no error named it.
Retry vs dead-letter is explicitEvery bundled sink classifies each error as transient or permanent (§7.2). A concurrent-upsert race between pods is retried, not dead-lettered.
At-least-once, idempotentA crash between bulk write and commit re-flushes the batch; upsert semantics make that safe.
Losses are loudA dirty key whose payload is gone at flush time gets ErrPayloadMissing (via OnFlush), an error log, a RecordUnflushedExpiry count and a DLQ entry. Any non-zero count should page.
Degraded mode keeps orderDirect writes happen only when nothing older is pending for the key; otherwise ErrDegradedWriteUnsafe. Retry it; don't ack it.
Survives script-cache lossEvery Lua call site reloads and retries once on NOSCRIPT.
No crash on sink outageOnFlush receives an empty, non-nil result alongside the error when a sink fails outright; up to 1.0.7 this dereferenced nil and crashed the flush goroutine.
Run the journal on durable Redis. Use maxmemory-policy noeviction (eviction would drop unflushed state) plus AOF and replicas, or MemoryDB. ElastiCache alone does not persist unflushed writes across node loss. The bundled docker-compose.yml now runs Redis with noeviction and appendfsync everysec on a dedicated volume, so a local crash loses at most ~1 s of unflushed writes.

What remains is the class of loss no in-Redis mechanism can detect: losing Redis itself (node loss, failover to a lagging replica, FLUSHDB) after the ack. That is the subject of the proposed event ledger on the roadmap (§12).

Section 07 · New in 1.0.8

Datastores & deployment topologies

sluice never parses your data and never creates tables or emits DDL. Your contracts define the data shape and your migrations own the schema. That is what lets the same journal sit in front of three very different stores, each with a different bottleneck to remove.

7.1 · Adapters

Store Sink (write) Source (read) Bottleneck removed
DocumentDB / MongoDB sink/docdb: unordered BulkWrite source/docdb: FindOne; Find for bulk Per-write index I/O on a single primary; connection caps
DynamoDB sink/dynamodb: BatchWriteItem in 25-item chunks, UnprocessedItems mapped back to their keys and retried with backoff source/dynamodb: GetItem with ConsistentRead: true; Query for bulk WCU spend: bursts flatten to a low, steady provisioned baseline; lookups use Redis indexes instead of GSIs; idempotency uses SETNX instead of TransactWriteItems

Bring your own store by implementing two small interfaces. In 1.0.8 the Source interface gained ReadBulk:

// write side
type FlushSink interface {
    BulkWrite(ctx, models) (*BulkWriteResult, error)

    Ping(ctx) error
    Close(ctx) error
}
// read side, symmetric by design
type Source interface {
    Read(ctx, model) ([]byte, error)
    ReadBulk(ctx, model) ([]BulkReadResult, error) // new

}

NewSourceWithClient / NewSourceWithPool let the sink and source share one connection pool. source.ErrRecordNotFound is translated to the public sluice.ErrRecordNotFound, so callers never import the source package for error handling.

7.2 · Error classification

The engine never infers success, so every sink must say, per key, whether a failure is worth retrying. How each bundled sink classifies failures:

Sink Transient (retried) Permanent (dead-lettered) Whole batch retried
sink/docdb 11000 on _id_ for an upsert (a race with another pod) Any other write error, including 11000 on a business unique index Write-concern error, network or context error
sink/dynamodb UnprocessedItems, context cancel/deadline Bad Update type, missing PK/SK, marshal failure, duplicate key in the batch, per-item PutItem failure after a ValidationException fallback An unprocessed item that can't be mapped to a key; any other API error
sink/postgres Any other SQLSTATE 23xxx, 42P01, 42703, 21000; a row whose columns differ from the batch's first row; a duplicate conflict key in the batch A non-Postgres error, e.g. a connection failure

On a permanent multi-row error, sink/postgres retries the batch row by row, and on a batch-wide ValidationException, sink/dynamodb falls back to per-item calls, so only the bad rows are dead-lettered. A custom sink reports per-key failures the same way:

res.Errors = append(res.Errors, sink.SinkError{
    CorrelationKey: m.CorrelationKey,     // empty → whole batch aborted (ErrUnattributedSinkError)
    Code:           code,                 // store-specific; optional
    Class:          sink.ClassPermanent,  // or sink.ClassTransient
    Err:            err,
})

ClassUnknown (the zero value) keeps the legacy rule: dead-lettered if Code == 11000, otherwise retried. SinkError.IsPermanent() implements the rule, and sink.CheckAttribution(models, result) is the same guard the engine runs.

9.2 · Write path

Method Semantics
Write(ctx, user, payload) Journals the event; nil means durably journaled and safe to ack. On a hot key, also raises the hot flush trigger. When Redis fails, writes direct only if order-safe, else ErrDegradedWriteUnsafe.
WriteIdempotent(ctx, user, payload, msgID) Write guarded by SETNX EX. Replays return ErrDuplicateIdempotencyKey so consumers can ack without re-journalling.
OnFlush(callback) Invoked after every bulk write attempt, success or failure, with the keys, a non-nil result and the error (including ErrPayloadMissing).

9.3 · Read path & regime

Method Semantics
Read(ctx, user) L1 → L2 (with lazy refresh) → Source, hydrating on the way back. Absent everywhere → ErrRecordNotFound.

Tuning heuristics.
  • Set FlushWindow to the staleness your readers tolerate; nothing else bounds it.
  • Size Redis for the worst-case backlog, not the steady state: unflushed state never expires, and under noeviction a full Redis refuses writes.
  • Set ActivityWindow from session length (p95 login-to-logout), not from memory fear; watch hot_set_size instead.
  • Size L1 from its hit ratio, and use ReadFresh rather than a tiny LocalTTL for reads that need strict consistency.
  • Enable WithBatchedWrites only when per-write Redis latency, not the datastore, is the bottleneck.
  • Page on any non-zero unflushed_expiry_total.

Section 12

Closing

sluice is best understood as four decisions stacked on each other. First, that Redis should be used as a journal rather than a cache, which buys atomic absorption and free coalescing. Second, that band partitioning with hash tags makes the journal parallel and cluster-legal by construction rather than by care. Third, that the journal's contents are worth serving back, through an in-process tier, a hot/cold regime and set-based pre-warming, turning a write-optimised buffer into the fastest read path in the system for exactly the keys that matter right now. And fourth, the one 1.0.8 made explicit: an acknowledged write is never dropped quietly. It reaches the store, the DLQ, or an alert.

The result is a library where the caller contributes a few small functions and receives, in exchange, a crash-safe, deduplicating, idempotent, cluster-aware, self-healing data plane for DocumentDB, DynamoDB, PostgreSQL or a store of their own, validated end-to-end against real Redis, Valkey cluster, MongoDB, DynamoDB Local, PostgreSQL, Kafka and LocalStack.

What's next

  • Event ledger and reconciliation (RFP #17, proposed): an opt-in record of acknowledged writes kept outside Redis, in an embedded Pebble store backed by object storage, plus a Reconcile job that finds and repairs keys whose datastore state is behind what was acknowledged, for example after losing Redis. By default it never affects Write's result.
  • Strict mode (RFP #19, proposed): payment-grade namespaces with durable acknowledgement (WAIT/WAITAOF or a durable store such as MemoryDB), conditional writes (WriteIf) and a store-side version guard that stops an older flush from overwriting a newer version.
